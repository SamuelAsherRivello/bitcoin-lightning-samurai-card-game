# Research: Theme Reorganization

| Decision | Rationale | Alternatives Considered |
| -------- | --------- | ----------------------- |
| Keep `bevy/crates/game/assets` as the Bevy asset root and add `themes/theme_japan` below it | Bevy already resolves runtime asset handles relative to `assets`; preserving the root avoids desktop and web asset plugin changes while still satisfying the theme grouping requirement. | Changing the asset root to `assets/themes` was rejected because shared shaders and future shared assets would become awkward and browser export assumptions would be riskier. |
| Use category-prefixed theme folders: `card_*`, `location_*`, and `world_*` | The spec requires category identity in names while theme identity comes from `theme_japan`. Folder names are stable references for registries, docs, and tests. | Keeping `card_type_*` was rejected because 009 now separates data as `CardModel` from rendering as `CardViewBundle`. |
| Treat the card back and safe-area reference as theme card-category assets | Both files participate in `CardViewBundle` presentation for the Japan theme and are not reusable generic assets as currently named. Keeping them under `theme_japan/cards` makes card view contents discoverable from the card category. | Leaving card structure assets under `assets/cards/card_structure` was rejected because developers would still need a non-theme folder to understand complete Japan card presentation. |
| Keep shaders outside `themes/theme_japan` as shared assets | `card_background_mask.wgsl` is implementation support and is not a card, location, or world identity. Keeping it shared preserves the distinction between theme-owned presentation assets and reusable rendering support. | Moving all assets under the theme root was rejected because FR-024 preserves a shared-asset distinction. |
| Update explicit registry paths instead of adding runtime directory scanning | Current resources define the small, bounded card, world, and location set. Explicit paths are testable, deterministic, and preserve current behavior. | Runtime discovery was rejected because it would add ordering, filtering, and browser packaging risk without a feature requirement. |
| Use Scene/Model/View naming for app structure, data, and visuals | `AppScene` names the always-present app-level scene, `GameScene`, `DeckScene`, and `DebugScene` name active sub-screen presentations, `CardModel` makes data ownership explicit, `CardView` names rendered presentation, and `CardViewBundle` names the Bevy bundle that creates the card visuals. This avoids overloading scene, model, and view terms. | Keeping `GameScene` and `DeckScene` as the active sub-screen names was rejected because the app intentionally keeps `AppScene` always present and loads a view on top. Keeping a generic bundle naming pattern was rejected because it does not clearly separate data from view. |
| Verify both desktop and browser check-only workflows | The constitution requires Windows desktop and browser WebGPU parity. Asset path changes are especially likely to fail differently in browser packaging, so both target checks matter. | Desktop-only verification was rejected because browser asset paths can regress independently. |
